从长期 Agent 运维经验中抽象通用方法，面向任意长耗时、多阶段、依赖外部系统的任务，例如构建部署、模型训练、数据管线、文档交付、仿真和异步审批。

1. agent项目成熟度判断

可以把项目成熟度分为四级：

级别 能力
L1 脚本化 能自动填表、调 API、上传文件
L2 可观察 有 watcher、日志、通知和状态台账
L3 事件闭环 watcher 能唤醒正确 Agent，Agent 自动继续
L4 自愈自治 多账号隔离、幂等、安全门禁、重启恢复、异常才找人

L4的目标是建立一套 事件驱动、所有权明确、状态可恢复、动作可审计的 Agent 工作流系统：

  • 主 session 负责全局调度、事件路由和异常决策；
  • durable worker 负责一个明确任务及其资源的执行与续作；
  • 外部 watcher 负责低成本观察长流程，不让模型在前台反复轮询；
  • 通知总线把变化送回正确的主 session 或 worker；
  • 浏览器、CLI、API、版本库、存储和验证工具构成执行面；
  • ledger、checkpoint、iteration ledger 和版本证据构成状态与审计面；
  • 人只处理必须授权、无法自动判断或涉及重大不可逆取舍的异常。

因此，准确目标是：正常路径自动闭环，异常路径按处理能力分级升级，人处于 on-call 状态，而不是完全取消人工。

这套方法适合任意长任务类型，但迁移至少需要：可查询的权威状态、稳定资源身份、可定义的阶段和交付契约、明确授权范围，以及可回读的动作结果。

2. 核心架构与八项原则

2.1 四个平面

2.2 八项核心原则

  1. 状态驱动：以外部权威 API、完整页面内容、最新报告和本地证据为事实，不凭 toast、按钮文案或旧记忆行动。
  2. 事件驱动：长耗时等待交给 watcher；Agent 不在模型回合中前台 sleep 或反复查询 API。
  3. 单一所有权：同一任务资源同时只有一个正式写入 owner；同一异步阶段只有一个有效 watcher。
  4. 精确身份：taskId、resourceId、账号、租户/项目、浏览器 profile、CDP 端口、exact URL 等适用字段必须匹配。
  5. 本地稿先行：本地工作稿或版本库是内容权威源，外部表单与附件由其同步；不能只改页面不落盘。
  6. 证据闭环：动作由 request/transaction、commit、SHA、manifest、报告和外部状态迁移等证据交叉确认。
  7. 失败关闭：身份不符、资源冲突、重复 watcher、版本不一致、必需授权缺失或状态不明时禁止危险写操作。
  8. 有界自治：真实、可归因、属于公开契约且已授权的问题由 worker 自动修复；真实性、合规与重大取舍不清时交给人。

3. 任务身份、入口与 worker lifecycle

3.1 标识与任务契约

本文统一使用以下概念，不把业务对象绑定到某一平台：

  • resourceId：被处理资源的稳定标识，例如一个训练任务、部署环境、数据集或交付记录；必要时使用租户/项目命名空间，避免跨系统重号。
  • taskId：当前编排任务/worker 的定向路由身份。进程替换或新建 worker 后可能变化，不能把历史 taskId 当永久收件地址。
  • runId 或 request/transaction ID：一次外部执行的身份，与资源、版本和 iteration 绑定。
  • iterationId：本地全生命周期的迭代编号，不等同于外部 attempt。

入口应先读取项目规则、资源配置、授权、容量/预算和外部可执行状态，再创建任务。为每个任务明确：目标、输入、可修改范围、验收条件、最长等待时间、迭代/成本上限、终止条件和人工升级边界。

推荐持久配置包括 config/accounts.json、config/resources.json、docs/current_tasks.json，以及资源专属 runs/<resourceId>/。是否能够执行某动作应由外部权威状态与预检共同确认，不能仅凭本地“可执行”缓存。

3.2 标准生命周期

确认确有未完成动作，查找现有 owner
  → 创建唯一 durable worker，分配独占资源
  → 读取 worker 规则、方法文档、项目 notes、ledger/checkpoint
  → 读取完整通知/评论，核验身份、授权、外部权威状态
  → 开始 iteration，记录 baseline、假设与计划
  → 本地制作或修复，完成可复现验证
  → 安全预检，同步并回读外部版本
  → 执行唯一事务，保存 request/run 证据
  → 若仍有依赖外部变化的未解决动作：启动唯一 watcher
  → arm_notification_wait，释放模型回合但保留等待中的 worker
  → watcher 定向通知，同一 session 被唤醒
  → 重读 checkpoint 与权威状态，继续验证、修复或交付
  → 交付被接受且无活跃修复/未解决动作，或任务达到明确终止条件
  → 写 checkpoint、ledger、经验与 changed files，释放资源并退出

关键是 外部观察者 + 有界等待租约 + 原 session 唤醒，不是让 worker 无限占用前台推理。

3.3 等待、交接与退出不能混淆

  • 每次提交或收到平台状态通知后，必须重新查询权威状态，再判断等待还是退出。
  • 若交付已被外部系统接收、进入其处理流程，且当前 worker 没有活跃修复或明确未完成动作，应持久化交接状态后退出。外部尚未最终完成，不等于原 worker 必须留驻。
  • 后续审批、回退或评论可以由独立 watcher 继续观察。原 owner 已退出时，应路由到主 session，由其核验待办再创建或恢复合适 worker，不能持续投向旧 taskId。
  • 只有确有未解决动作依赖外部变化时才建立 durable wait。明确人工阻塞应记录原因、证据和下一责任人；不要伪装成持续工作或成功。

“退出执行 worker”“外部接受交付”“业务最终完成”是三件不同的事，必须分别记录。

4. Watcher 职责、通知路由与分级

4.1 按职责拆分 watcher

通用类型 职责
notification watcher 保存完整通知、评论、提及及其唯一 ID，分类路由
status/review watcher 观察固定资源的外部状态、交接结果或修复请求
ledger watcher 观察当前台账的业务状态差异
capacity/opportunity watcher 观察任务队列、可用容量、配额或执行窗口
run watcher 绑定某一次构建、训练、仿真、导出或报告生成
resource supervisor 检查浏览器、连接、容器或其他专属资源健康，执行已授权的有界自愈
recording watcher（可选） 仅在确需录屏的工作流中观察录制健康，不决定内容交付是否合格

watcher 默认只读：获取权威状态、比较快照、落证据并通知，在终态、超时或不可恢复错误时退出。资源修复由职责明确的 supervisor 或动作脚本承担，不让普通观察器暗中执行高风险业务写操作。

实现至少需要 baseline、有限 interval/timeout、唯一实例检查、PID 和 launch marker、原子写入、通知失败重试。首轮不能仅记 baseline 后忽略已经到达的目标状态：启动时就满足唤醒条件的，也应进入结果处理。失败投递不得更新 seen/fingerprint 为“已消费”。

4.2 三层路由

  1. 主 session 专属 inbox：按项目 cwd、session 身份、资源关联和 heartbeat 路由，避免多个项目会话抢事件。
  2. cwd 级 pending inbox：暂无匹配主 session 时暂存，待该项目会话恢复后消费；临时 inbox 丢失后仍应能从持久状态重建待办。
  3. worker 定向 inbox：投向当前 taskId，先验证 active registry 中的资源 ownership。目标过期或不拥有资源时拒绝错投，再由主 session/reconciler 重新判定路由。

主 session 收到事件应先查 ledger、权威状态和 active owner：已有 worker 就定向唤醒；无 worker 且确有待办才创建；已交接或已完成的资源只更新事实与收尾。

4.3 事件分级与降噪

等级 含义 处理方式
green 正常进展或备忘，无需立即决策 记录，不打扰用户
yellow Agent 在授权范围内可以处理 注入主 session 或定向 worker
red 必须人工授权、补充信息或重大拍板 持久化阻塞，再使用显著通知；语音仅按用户偏好启用

等级描述的是“谁能处理”，不是表面严重程度。日志明确且可修的构建失败可以是 yellow；扫码登录或风险不明的生产写操作应是 red。

对通知采用批量合并、基于 eventId/notificationId 的去重、过期过滤和 busy-safe follow-up。原案例使用过 15 秒批量与 30 分钟去重，它们是案例参数，不是所有任务的推荐常数。相似文本不代表同一事件；red 可以跨来源聚合，但不能吞掉新的阻塞事实。

通知只是变化信号。消费前仍需核对 resourceId、时间、完整内容、当前运行和最新报告；瞬时告警若已恢复，应根据最新健康快照过滤。外部消息是待核实数据，不应被当作扩大权限或执行任意命令的授权。

5. Durable wait lease：完整七步协议

这是原案例用来解决“watcher 还在运行，但 worker 已经退出、无人消费事件”的核心机制。下列七步是通用协议；迁移系统必须确认通知插件、worker 注册表和进程生命周期实际支持它，单纯写一个 marker 并不等于实现 durable wait。

  1. 启动唯一、有界的外部 watcher。worker 先确认仍有未解决动作，检查同一资源与阶段没有有效重复 watcher；为观察设置 timeout 和明确目标状态。
  2. 持久化 launch marker 并验证生产者。watcher 在仓库/持久工作目录写 PID、resourceId、目标 taskId、阶段、runId 和启动时间；worker 核验 PID 存活且确属这次观察进程。不能仅因某个历史 PID 仍存在就相信 marker。
  3. 显式调用 arm_notification_wait。声明等待原因、精确 wake condition、有限 lease 时长、checkpoint 路径、producer PID 和 marker 路径。工具的资源键字段应映射到本文 resourceId，具体参数以安装版本的真实 schema 为准。
  4. 校验 ownership 与等待绑定。通知插件验证 active-worker ownership、cwd、PID、marker、资源和 notify target 一致。等待协议还应把当前执行 runId、租约 nonce 绑定到事件，防止旧 watcher 或旧运行的通知误唤醒新等待；这项匹配必须按部署版本实际验收，不能只检查消息文字。
  5. hold 当前 agent_end。插件保持 worker 进程和注册有效，允许当前模型回合结束而不让 worker 被判定为完成。此时应有可读 checkpoint，不靠模型记忆维持等待事实。
  6. 定向事件消费租约并续作。watcher 发送匹配当前任务、资源、运行和租约身份的事件，插件排入 follow-up、消费对应租约，恢复同一 session。worker 重读 checkpoint、marker 和外部权威状态后继续；事件到达本身不证明外部任务成功。
  7. 到期触发自检，不静默成功。租约到期应唤醒自检，核对外部任务、生产者和身份，决定继续观察、修复、升级或退出；若续租，应使用有效的当前绑定，不能无限延长而无判断。

启动 watcher 与 arm 之间存在状态变化窗口，实现应保证事件不会因尚未 arm 而丢失，也应测试 busy 时、重复事件、过期事件和 watcher 异常退出的行为。原文记载的定向唤醒与 wait lease 测试是原案例证据，不替代目标系统的端到端验收。

6. 资源隔离与健康管理

6.1 资源绑定

有浏览器需求时，推荐绑定：

账号/租户 + resourceId
  ↔ 专属凭证文件或凭证引用
  ↔ 独占 Chrome profile
  ↔ 独占 CDP 端口
  ↔ exact URL / target
  ↔ 当前唯一 worker taskId

非浏览器任务则把相同原则用于工作目录、容器、云任务、存储前缀、锁和部署环境。任务拆分不应制造对同一资源的多个并发写入 owner；确需共享时必须明确锁、串行化或所有权交接协议。

隔离主要防止错账号、错页面、资源被其他 worker 关闭、凭证串用以及旧事件投向替代 worker。浏览器操作必须定位 exact URL/target，不能默认使用 pages[0]。清理只针对当前 worker 拥有的资源，禁止关闭共享浏览器、其他任务页面或无关容器。

6.2 通用资源健康管理

资源管理可分为三层：

  1. 观察：检查进程、连接、容器、磁盘和其他执行依赖，保存新鲜的健康快照。
  2. 有界恢复：按注册表和所有权重连连接、恢复专属进程或重建可安全重建的资源；冲突或后果不明时失败关闭。
  3. 升级：恢复失败、缺少权限或需要重大不可逆操作时，记录证据并交给主 session 或用户决策。

资源健康只证明执行依赖可用，不代表产物通过验收或允许交付。健康检查与业务验收必须分别判断。

7. 通用执行闭环：本地、外部与版本证据

7.1 用公开契约驱动制作与验证

公开需求/输入契约
  ↔ 真实资源与运行环境
  ↔ 实现或交付产物
  ↔ 独立可复现验证

验证标准应能回溯到公开要求，不能靠隐藏限制或伪造材料获得“通过”。代码与数据任务按需覆盖边界输入、非法值、失败传播、幂等、旧输出清理、合法输入变形；依赖、超时、精度和 schema 应明确。文档任务则核实原始来源、事实、公式与适用范围，并验证文件结构和内容。

原案例使用容器与专用验证工具保证环境接近外部执行环境。可迁移的是“可复现、独立验证”的方法，不是要求所有任务安装同一专用工具或使用案例的业务评分规则。

7.2 外部同步不是上传成功就结束

本地权威稿 → 外部同步 → 回读版本 → 唯一事务 → 请求绑定 watcher → 最新结果 → 契约验证 → 有界修复或交付。

需要版本证据时，可组合使用：

  • 本地内容 hash、输入/配置指纹与逐文件 SHA-256；
  • Git commit、远端引用，以及适用时 HEAD == origin/main；
  • 上传产物的大小、文件名、对象版本、根 commit 和 manifest；
  • 实际执行绑定的 request/transaction/run ID；
  • 运行开始时间晚于最终有效保存时间，并核对输入指纹；
  • 报告与本次运行、attempt、版本的对应关系。

时间顺序只能辅助证明新鲜度，不能替代版本指纹。外部系统是否自动重新打包、表单保存是否更新运行输入、API 是否覆盖完整事务，都必须独立验证；原案例发现过“保存了但仍执行旧版本”的问题，不能据此推断所有系统的 API 都不可靠，也不能未经测试假定 UI 路径必然正确。

7.3 按任务选择工具

  • 浏览器任务优先 DOM/Playwright，图像理解用于真实图片或图表，不替代可查询 DOM。
  • 受限 Web IDE 可用编码传输并逐文件核验，避免终端输入丢字符；Git 推送与外部可执行包仍要分别确认。
  • 文档可用 python-docx、OOXML/ZIP 检查及 LibreOffice 打开验证；页数、结构、可编辑性、附件和最终需求要一致。
  • 研究型任务应保存 URL、访问日期、采用事实及适用范围，不凭记忆编造来源，也不把重制材料伪装成原始材料。
  • 外部反馈应读完整评论和锚点，按目标系统规定回复并回读结果；避免重复回复及泄露内部日志、凭证或无关技术细节，必要的自动化披露不得隐瞒。

有权威、受支持且完整的 API 时可以用 API；需要真实 UI 才能完成已验证事务时才用 UI。选择依据是授权、契约和证据，不是固定偏好。

8. 状态持久化、checkpoint 与 iteration

8.1 当前状态和原始事实分开

通用归一状态可采用：

queued / active / waiting_external / done / cancelled

名称可按项目调整，但须同时保存外部 raw facts、当前动作、责任人和阻塞原因。外部 accepted、运行 completed、交付 done 可能处于不同层次，不能直接混为一个“成功”。已交接并退出 worker 的资源仍可处于 waiting_external。

8.2 三层持久化与日志分工

  1. 全局 ledger：docs/current_tasks.json 保存每个资源的当前状态、账号/项目、当前 taskId、watcher、动作、阻塞和证据索引。用单写者、文件锁或事务避免并发覆盖，以原子写更新。
  2. 资源 checkpoint：保存最新权威状态及观测时间、身份绑定、已完成动作、当前请求、版本、watcher/lease、下一动作和“不得重复做什么”。另一个 worker 不依赖旧模型记忆就能接管。
  3. 长期经验：按项目约定沉淀已验证方法、可复现故障、领域规则和工具索引。可复用脚本与临时脚本分开；收尾时对临时产物执行 promote / defer / discard，分别表示正式化、待验证保留或丢弃。

日志回答“发生过什么”，ledger 回答“现在是什么”，iteration ledger 回答“各轮尝试是否有效”，checkpoint 回答“从哪里继续”，四者不能互相替代。完整通知、报告与大产物另存，ledger 留索引，不存凭证和无关个人信息。

session 保存上下文，checkpoint 保存最小恢复事实。即使可以原 session resume，也应先读 checkpoint 并回查权威状态；重启后历史 PID、lease 和 registry 不能直接当作活跃事实。

8.3 每轮 iteration 必须记录

iteration ledger 建议用追加式 JSONL，至少记录：

  • resourceId、taskId、iterationId 与触发事件；
  • 权威 baseline、问题归因、本轮 hypothesis 和修改方向；
  • 计划改什么、不改什么、授权与预算消耗；
  • 本地/外部版本指纹及实质 diff；
  • request/transaction/run ID、外部 attempt 与正式修复轮次；
  • 完整结果/报告索引、是否有效、是否引入回归；
  • 下一步继续修、回滚、交付、人工复核或停止。

本地迭代编号应全生命周期单调递增；外部 attempt 可能重置、对应多个报告或不计某些失败，因此只能作为外部字段，不能替代 iteration 身份。

开始新一轮前检查：是否重复已证伪假设、是否有实质变化、失败究竟来自内容/版本/环境/平台、外部是否实际使用新版本、剩余额度和停止线是什么。不要把版本同步失败当内容问题反复改，也不要用无界补丁掩盖真正根因。

8.4 建议目录

project/
├── .pi/agents/_worker.md       # 项目 worker 规则与终止条件
├── config/                    # 账号引用、资源和授权配置
├── docs/current_tasks.json    # 当前事实与路由
├── docs/task-routing.md       # 事件 → 权威读取 → 责任人的规则
├── docs/automation-methods.md # 已验证方法与可复现坑
├── runs/<resourceId>/
│   ├── checkpoint.json
│   ├── iterations.jsonl
│   ├── evidence/
│   └── watchers/              # launch/state marker
└── scripts/
    ├── watchers/              # 只读观察
    ├── actions/               # 有副作用动作
    ├── preflight/             # 执行前检查
    └── _debug/                # 未验证实验

目录是迁移建议，不表示当前仓库或任意部署已经存在这些组件。敏感运行记录即使放在持久工作目录，也不应误提交到公开版本库。

10. 调教过程：通用故障与演进路径

以下阶段来自原案例的演进概括，可用来规划迁移路线；并非每个目标系统都会按同一顺序实现。

10.1 从环境迁移到单任务可运行

先解决依赖、容器、路径、浏览器登录态和只读状态探测。原案例暴露过路径探测失败被误判为没有浏览器、猜测写接口，以及已有授权范围内反复询问的问题。

通用方法：先核验实际环境和授权清单，抓取/阅读真实接口契约，以可见流程处理必须的人机步骤；不硬猜写请求，也不把过去授权无限扩大。

10.2 从单任务到隔离并行

静默退出、provider/额度错误未上报、模型继承错误、注册表与真实进程不一致、reload 后工具或身份错位，以及主 session 包揽所有任务，都会破坏自治。

演进方向是独立 durable session、完成/错误通知、模型与上下文继承、active registry 和资源所有权检查。注册表必须与进程及外部状态交叉核验，不能只凭列表断言系统健康。

10.3 从共享资源脚本到资源编排

共享资源容易造成争用、误关闭、告警刷屏、恢复后旧告警仍注入；健康探测频率也不该决定通知频率。

演进方向是独占资源、supervisor/常规恢复/观察分层、冲突检查、状态变化通知和新鲜健康快照过滤。资源就绪不能被误解为业务可交付。

10.4 从“通知人”到“通知 Agent”

只写日志或播声音仍依赖人转述。原文记载过外部脚本 → 指定 worker → worker 继续响应的闭环测试。

迁移应补齐 cwd 隔离、定向 inbox、busy-safe follow-up、可靠消费和重试、唯一事件去重、完整通知存档及过期过滤。原案例的测试结论仅证明当时被测试的路径，不证明任意部署或所有故障场景。

10.5 从“watcher 活着”到“等待中的 owner 活着”

watcher 目录里有事件，不代表 settled/退出的 worker 能消费。演进方向是显式 arm、验证 producer PID/marker、绑定 ownership、有界 lease、hold agent_end 和到期自检，而不是一遇事件就人工 reload。

10.6 从分散通知到统一路由与收尾

通知进错 session、重复创建 owner、外部已经接收却不退出等故障，推动形成完整事件分类、当前台账、已有 worker 优先唤醒和终止规则。交付后先核验状态、持久化再退出；后续 watcher 与执行 worker 生命周期分离。

10.7 从“能执行”到“少迭代且可信”

后期优化应把反复出现的真实反馈前移为公开契约、真实性、环境验证和版本一致性检查。每轮记录有效性、根因和回归；对临时脚本做 promote / defer / discard，只把已验证方法提升为正式流程。

安全控制也可能误拦正常路径。拒绝应给 reason code、缺失事实和安全替代路线；可修复的前置问题进入修复流程，而不是原地空等。只有超出授权或判断能力时才升级给人。

11. 可靠性、安全幂等、版本证据与隐私

11.1 防重复与幂等

  • 同资源单一正式 owner，同阶段单有效 watcher；创建前先查所有权和实际进程。
  • 已有 running request 时禁止重复触发；提交只认权威状态迁移，不因按钮消失或响应超时重复提交。
  • 通知按唯一事件身份去重，已处理评论不重复回复；等待绑定与消费需要幂等。
  • 动作响应不明时先 reconcile：查实际请求、外部状态及证据，再判断是否重试。不能把“没收到响应”当成“动作没有执行”。

11.2 防错身份与旧版本

执行前核验账号、租户/项目、resourceId、当前 owner 和适用资源绑定。浏览器核验 profile、CDP 和 exact URL；非浏览器任务核验工作目录、容器、环境和存储目标。

版本检查沿完整交付链进行：本地内容 → 远端引用 → 实际执行输入 → request/run → 最新报告。任一环节不一致，先修复同步或绑定，不得使用旧报告证明新版本通过。

11.3 防危险捷径

安全门禁应在有副作用的工具调用前检查，而不是只写在提示词里：

  • 禁止绕过已验证完整事务、使用未确认写端点或跳过必要授权。
  • 禁止关闭共享浏览器、杀无关进程、覆盖其他任务资源。
  • 身份不符、状态不明、重复 owner/watcher、版本冲突时失败关闭。
  • 对删除、生产变更、签署、发布等不可逆动作单独定义授权和确认条件。

原案例的 raw execution、UI acquire 等具体拦截规则见案例篇；通用迁移应根据目标系统的实际危险路径重新制定，不能照搬端点黑名单。

11.4 凭证与隐私

Cookie、token 和其他凭证按账号/环境隔离并视同密码；本地敏感凭证文件可采用权限 600，不打印内容，不写入公开仓库、通知和 checkpoint。认证失效时停止相关写操作并请求重新登录，不猜测或绕过认证。

材料、运行日志与外部回复遵守真实性、授权、版权和脱敏边界。checkpoint 应保存凭证引用而不是凭证值；事件、报告及恢复目录也要配置访问权限和保留期。

12. 自治边界与冷启动能力

12.1 可自动化范围必须逐项验收

在授权、契约和工具链都已验证的前提下，目标系统可规划自动完成：任务发现与分派、本地制作与验证、外部同步、长运行等待、事件处理、有界修复、交付回读和经验沉淀。资源自愈也仅限已授权且可判断后果的操作。

这是一份可实现范围清单，不是任意新项目已经具备这些能力的承诺。业务流程中的考试、签约、提交等动作是否可自动执行，还取决于本人授权与目标平台规则。

12.2 必须人工或明确授权的情况

  1. 超出既有权限范围的操作，以及必须由本人完成的授权或确认。
  2. 登录失效、扫码、验证码或平台风控。
  3. 必须由本人提供或确认的身份、真实材料和操作授权。
  4. 真实性、隐私、版权或合规边界不清。
  5. 重大不可逆决策、放弃任务、重大方向变化或申诉立场。
  6. 平台故障、provider 限额、网络异常且无法判断动作后果。

升级应带上当前事实、证据、已尝试动作、可选方案和需要人确认的具体问题，不把可自动修复的普通失败一律交给人。

12.3 运行中自治不等于重启后零人工恢复

运行期间自动闭环、checkpoint 可恢复、断电重启后零人工恢复是不同能力，必须分别验收。不能因为运行中的流程成功，就认定机器或进程重启后也会自动恢复。

目标系统的冷启动验收至少需要：

  • 电源/防休眠配置持久化，watcher/supervisor 的服务或 LaunchAgent 开机拉起。
  • 浏览器/CDP/profile 或其他资源注册表恢复，并重新验证实际占用。
  • 主 session 自动启动、cwd 级 pending 事件消费和正确 worker 路由。
  • 临时 inbox、worker registry、wait lease 丢失后的持久 checkpoint 重建。
  • 逐资源回查外部权威状态，避免重复评测、提交、发布或创建任务。

登录、权限变更和机器故障仍可能构成人工边界。恢复历史记录不是复活历史 PID 或直接相信旧租约。

13. 后续三项可以改进的地方

13.1 统一 reconciler

启动或重启后，合并读取账号/资源配置、当前 ledger、checkpoint、active-worker registry、资源健康、watcher PID/marker 和外部状态/通知。先输出唯一动作计划：恢复、唤醒、新建、退役、继续观察或 red，再按授权与门禁执行。

reconcile 必须以最新权威事实消除冲突，不能把历史台账当作实际运行，也不能为同一资源创建两个 owner。

13.2 将关键事实移出临时目录

/tmp 只保存可重建的 inbox 副本、短期缓存和运行锁，不作为唯一事实源。launch marker、checkpoint、iteration 和动作证据写到持久工作目录；启动时由持久状态和外部回读重建路由、registry 与必要等待。

持久状态本身也应原子写入、备份并控制权限，不能只把目录从 /tmp 换个名字。

13.3 端到端健康检查

定期验证一条无业务副作用的受控链路：

外部只读探测/测试事件
  → watcher 发现
  → 通知总线路由
  → 主 session/worker 收到
  → ledger 更新
  → 回执 marker

同时检查资源连接、进程、session、服务管理器、电源设置和磁盘空间。健康检查要验证真实消费及回执，而不只是“进程还活着”；测试事件不得触发生产提交。
