本文是 eXpert 无人值守案例, 重点说明如何把网页操作、文件处理、模型运行和飞书通知封装成工具。

eXpert项目相对接口来源更丰富, 状态更复杂. 但是流程更简单. 用于测试我们工作流的移植难度.

1. 读取、撰写与上传技术栈

1.1 读取问题：文件

飞书网页版和浏览器混用

环节 技术 / 工具 本案例用途与限制
飞书 Doc / Wiki 正文 CDP、页面 DOM、内部滚动容器；feishu_doc_dump.py 提取已打开文档的正文并落盘；逐段滚动文档内部容器，不能只滚动 window 或读取当前可见段落
按链接读取文档 CDP 临时标签页；feishu_doc_fetch.py 打开指定链接、等待加载、调用正文提取，再关闭自己创建的标签页；不关闭用户原有页面，不修改文档
引用文件链接提取 页面导航 hook、真实点击；feishu_doc_links.py 提取没有普通 href 的引用文档链接；可能点击条目并新开标签页，不是完全无页面副作用，只清理本次创建的页面
飞书多维表格 页面 SSR 数据、页面内 fetch、gzip/base64 解码；feishu_base_read.py 读取字段、视图和记录；canvas 网格不能靠 body.innerText 获取，权限不足或数据源缺失须明确返回失败
canvas 字段与视图读取：已实现的解决路径 CDP、read_ssr()；window.bitableClientVarsForMkt.data.tableJson 不读画布文字，直接取页面已加载的 fieldMap、viewMap、recordMap；获得列名、字段类型、单选项枚举、视图定义和记录值
SSR 记录不全时补齐 页面内 fetch、api_records()、offset/limit 分页、base64 解码与 gzip 解压 当 SSR 缺失记录或只含部分窗口时，调用 /space/api/v1/bitable/<baseToken>/records，解码响应中的 data.records，按 recordId 合并记录；不再靠滚动画布或 OCR 猜行内容
不打开网页的定时读取 feishu_base_read.py --direct、read_direct()、已有登录 session、列元数据缓存 浏览器模式先保存列定义及 wiki→base 映射；后续直连 records API 分页读取，用缓存还原字段名和单选项。无需新建标签或抢前台；缺缓存/授权失效时返回结构化 error，不能绕过权限
页面接口数据 浏览器 SDK、页面内 fetch；xpert_page_fetch.py 取得依赖客户端签名的结构化数据；HTTP 200 仍需区分 JSON、空数据和 SPA HTML，查询入口不代替正式写入工具
云端文件取回 CDP 下载控制、文件卡片定位；doubao_grab_file.py 从文件卡下载实际产物，区分找不到卡片、按钮缺失和下载超时；历史脚本有特定目录依赖，跨任务复用前须核实源码

1.2 读取问题：消息

环节 技术 / 工具 本案例用途与限制
会话列表与最新消息预览 CDP、限定客户端节点读取；feishu_feed_read.py 取得 feed/chat 身份、latestMessageId 和预览；预览不是完整正文，不能按标题直接驱动后续动作
已加载消息正文 客户端消息模型、内容白名单；feishu_message_model_read.py 提取当前已加载的正文；页面未加载的消息不能据此认定不存在，也不保证完整历史覆盖
官方消息 API 读取 lark-cli、独立只读 profile；feishu_message_api_read.py 在独立应用身份和已授权 scope 下读取；不负责登录授权，不自动更换共享应用，跨租户可见性仍需核实
完整正文缓存 JSON、flock、原子写入；feishu_message_cache.py 保存已经取得的完整正文；仅在聊天身份与 messageId 精确匹配时回退，不按相同标题套用旧正文
主会话受控补读 CDP、单次聊天打开、硬截止；feishu_task_notice_read.py 缓存和已加载模型不足时，受控取得精确消息正文；需要对应读取授权，可能触发客户端正常已读语义
定时采集与投递 launchd、只读 watcher、Pi 通知；watch_feishu.py、watch_dm.py 定时读取新消息并交给 Agent；采集、发布和 Agent 消费分别记录，不能把投递成功当作正文完整
通知健康检查 分层健康报告、受控 canary；xpert_notify_health.py、install_notify_health.py 检查服务、读取和通知消费；允许 transport=PASS/read=FAIL 的降级状态，健康频率与消息采集频率独立

1.3 撰写问题：Pages / Numbers

环节 技术 / 工具 本案例用途与限制
文档撰写与导出 Markdown/HTML、textutil、RTF、Pages；xpert_office_native.py 将文本、标题和表格组织为文档，经 Pages 导出 DOCX/PDF；自动化的是文件生成与导出，不是任意操作当前前台文档
表格撰写与导出 CSV、Numbers、Excel 格式导出；xpert_office_native.py 将本地表格数据交给 Numbers 导出 XLSX；源文件、输出位置与结果文件需明确绑定
授权范围限定 allowedRoots、显式 source/output-dir；xpert_office_export_scoped.py 只处理允许目录内指定文件，不把整个工作目录或内部记录自动转成附件
App 文档定位 AppleScript、opened-document reference 操作本次明确打开的文档，不使用用户当前 front document，避免焦点变化导致写错文件
并行与暂停控制 非阻塞 flock、Office 全局暂停状态 多 worker 不并行控制同一 App；局部获准导出不解除其他操作的暂停
导出结果检查 返回码、文件存在性、大小及文件结构/元数据检查 导出失败或预期文件未出现时返回失败；得到文件不等于已经上传，文件格式检查也不代替内容正确性检查

1.4 上传问题

环节 技术 / 工具 本案例用途与限制
上传计划生成 显式字段/附件清单、文件 hash；xpert_5th_make_submit_plan.py 指定目标记录、字段及文件，绑定 baseline；不默认 glob 目录，不由工具猜测该上传哪些文件
附件选择与上传 CDP chooser 拦截、文件节点绑定；xpert_5th_attachment_upload.py 将白名单文件注入准确上传入口；当前入口有有限记录范围，不能不经检查当作任意记录的通用上传器
表单与字段操作 CDP 节点定位、真实鼠标/键盘输入；xpert_5th_submit_ui.py 执行具体页面动作并全量回读字段；文件已选中或节点已注入不代表服务端已持久化
上传与写入编排 preflight、baseline 比较、flock、checkpoint；xpert_5th_submit.py 串行控制写入与附件动作，完成前核全集；响应不明先保存现场并重读，不能直接重复上传
请求与事件超时 WebSocket、绝对 deadline、事件数量预算 有界等待 chooser、CDP 响应和上传相关事件；超时返回未确认，不让工具调用无限阻塞
服务端落库确认 fresh snapshot、附件数组、即时及约 50 秒延迟回读 检查名称、大小、数量及目标绑定，再推进最后状态；避免附件未落库就将页面锁为只读
重复附件检测 完整附件计数，而非仅 name→size 字典 区分同名多份附件；部分旧行级工具仍会折叠重复件，不能等同正式核心的全集核验
内容一致性边界 本地 SHA-256、上传溯源、远端验证标记 当前核心仍保留 remote_sha256_verified=false；名称/大小匹配不等于远端内容 hash 已验证

2. 本案例的成熟度判断

可以把项目成熟度分为四级：

级别 能力
L1 脚本化 能自动填表、调 API、上传文件
L2 可观察 有 watcher、日志、通知和状态台账
L3 事件闭环 watcher 能唤醒正确 Agent，Agent 自动继续
L4 自愈自治 多账号隔离、幂等、安全门禁、重启恢复、异常才找人

当前大致处于 L2 到 L3 之间：

  • 已经实现大部分的自动化读取/运行/填写；
  • 运行中的正常业务路径尚未完全闭环, 有时依赖人工通知；
  • 安全门禁尚无保证；

3. 本案例的调教过程与故障演进

阶段一：跑通任务对接（9 月 24 凌晨）

最初目标是关注的是现成浏览器里的实际业务, Agent 围绕当前登录态探索站点、读取资格和申请流程，逐渐把重复动作整理成 CDP 客户端、卡片扫描和报名脚本。

这里的转折是飞书。我希望它以后也能操作飞书，而 Agent 起初仍在桌面客户端、OCR 和截图路线里探索。Agent 随后转向飞书网页版 + CDP，在真实登录态下读取页面结构和消息。历史会话记录了扫码登录、本人入群及随后读取到群消息的过程。

这一阶段的主要收获是：一组能复用本人浏览器现场的基础工具。

阶段二：迁移和单机可运行（2026-09-24—25）

Agent 当时报告已在 Mac mini 验证浏览器、飞书读取和资格扫描；这是历史记录，本次整理没有重跑这些操作。

固定工作目录、项目 skill、README 和迁移记录随后成为接手入口

阶段三：解决并行暴露出资源所有权问题（2026-09-26—30）

解决方式和talent类似, 要求隔离worker/gui/其他项目的资源.

Pages/Numbers 又暴露了同类问题。它们是共享 GUI 应用，多个导出进程使用 front document 时，可能把另一个 worker 的文档导出到当前文件名下。旧文件还在，也可能被误报成“导出成功”。后来的 scoped 导出入口把约束放进执行代码：限定授权目录、显式选定文件、使用本次打开的 document reference、锁定共享应用，并尊重暂停状态。

但是仍然需要手动调整, 资源隔离的能力agent并不会自动学习历史目录得到.

阶段四：已经解决过的接口问题再次出现（10-12）

deekseek可以复现自己的路径, 但是自动化能力不够. gpt自动化能力足够, 但是隐藏步骤, 导致已经取得成功连接的接口回退.

每出现问题人工要求agent写skill总结经验.

阶段五：安全/合规性问题（10 月 14）

agent反复拒绝自动化请求. 和talents不同的事, 整个系统并不是我手动一步一步搭建起来的. 所以并不是最小化实现, agent自己读取并添加了非常多不适用的安全限制, 导致无法正常工作. 模型把“安全”设为敏感词了, 所以即使是自己添加的所谓限制, 也足够打断所有自动化进程, 让agent完全停摆. 除非用自部署本地模型解除限制, 目前没有什么好的解决方案.
