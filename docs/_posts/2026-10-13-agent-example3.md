> 本文是 QuantNight 项目的量化回测自动化搭建与工程调教案例，重点记录如何将复杂的 WorldQuant Brain 量化平台交互、Tauri 桌面端、Rust/taskctl 底层进程守护、长耗时回测状态机与并发防崩体系跑通。  
> 相比纯 Web/API 任务，量化回测系统面临平台回测延迟大、并发配额限制、系统级进程监控、数据库与文件锁竞争等多重挑战。**本项目当前处于 L1~L2 阶段（强工具化与高可观察性）**：底层任务控制内核与鲁棒性门禁已搭建完毕，而 Session 级 Goal 驱动与 Agent 事件通知闭环尚未正式接通。本文结合实际会话中的排障历程，沉淀系统工程底座的建设经验。

## 1. 案例概览

QuantNight 不是简单的自动化脚本合集，而是一套运行在 Mac 环境上的 **量化回测、Alpha 挖掘与桌面端交互协同的自动化流水线**：

- **Pi 会话与运维**：主要用于全局架构重构、排障定位与阶段性维护（如维护 session `01a16328-d448-72d8-b75b-0552e1d06a4e`）；
- **任务目标管理（Goal）**：**【演进中 / 尚未接入】** 当前任务仍由人工或独立指令派发，长期自主 Goal 状态机尚未挂接到日常回测循环；
- **底层 CLI（`taskctl` / `task-core`）**：由 Rust 编写的原生任务控制核心，统领任务生命周期（创建、生成、启动、暂停、恢复、归档、删除）与并发排他；
- **桌面端（`quantnight-frontend`）**：基于 Tauri + 前端构建的桌面管理界面，为主控提供直观的状态卡片、折叠详情、诊断与手动控制；
- **回测执行后端与 MCP（`quant_night_mcp`）**：对接 WorldQuant Brain API，负责回测模拟派发、结果轮询收集、配额管理与进程隔离；
- **状态监控与通知（`watch_quant_task` / `agent-notify`）**：**【基础设施已具备 / 待业务接通】** 底层 kqueue 监听与通知投递链路已修复，但尚未作为主链路自动闭环唤醒 Agent 续作；
- **持久化层**：本地 MongoDB 存储海量 Alpha 回测表现（`alpha_results`）与任务定义，本地 `.quantnight/` 存储互斥锁与快照。

### 1.1 通用机制在本案例中的映射与当前进展

| 通用机制 | QuantNight 的具体对象与实现 | 当前实现状态 |
| --- | --- | --- |
| **目标编排（Goal）** | 自主根据 Pyramid 缺口与数据集画像编排长期回测计划 | ⚠️ **尚未接入**：当前依赖人工在前端或命令行指定具体任务批次 |
| **任务所有权** | 每个回测任务（如 `glb_borrowed_fields_r4`、`chn_d1_notown_...`）对应独立任务 ID 与专属锁 | ✅ **已落地**：Rust task-core 强约束 |
| **外部状态观察** | `watch_quant_task` 监控平台模拟进度、日志产出、tmux 消费者活跃度与 MongoDB 写入 | ✅ **已落地**：kqueue / 日志探针正常工作 |
| **事件路由** | watcher → `notify_agent.py` → JSON 事件 → `pi-agent-notify` 唤醒 Agent | ⚠️ **待接通**：底层通路由本次排障打通，但未闭环接入日常调度 |
| **长等待恢复** | 平台长耗时回测释放前台进程，由通知事件定向唤醒同一 session 续作 | ⚠️ **待接通**：目前主要依赖前端/CLI 状态展示与人工再确认 |
| **执行资源隔离** | 统一基于系统原生 `tmux` 会话隔离 Python 回测消费者；任务级 `flock` 文件锁隔离并发操作 | ✅ **已落地**：剔除 rmux，彻底收敛到系统 tmux |
| **并发与原子性** | 数据库写回采用 **CAS（Compare-And-Swap）**；进程控制采用 **Mission 锁**（非阻塞 flock） | ✅ **已落地**：防止并发交错与旧结果覆盖新状态 |
| **业务完成条件** | 平台权威模拟完成且成功入库本地 Mongo；单批超时/回执过期进入降级容错，不阻碍主线 | ✅ **已落地**：Fail-open 容错与无阻塞继续 |
| **人工升级** | 平台凭证彻底失效、网络无法恢复的持久中断、涉及不可逆策略删除与架构修改 | ✅ **已落地**：明确的人机协作红线与行为披露门禁 |

## 2. 从任务生成到回测收割的业务闭环

### 2.1 任务生命周期与双模状态机

QuantNight 的任务管理划分两大类别与严格的状态转移矩阵：

1. **普通任务（Regular）与 Super 任务**：
   - 经历 `pending`（待生成/待派发）→ `generating`（生成表达式）→ `ready`（准备就绪）→ `running`（回测运行中）→ `completed`（全部完成）/ `paused`（已暂停）/ `failed`（失败）；
   - 在 `generating` 阶段，复杂策略表达式展开可能耗时数分钟，超时机制必须分层；
   - 在 `running` 阶段，Python 消费者在后台 tmux 中异步调用 WorldQuant Brain 接口，支持批量模拟与增量收集。
2. **Priority 任务（高优先级队列）**：
   - 具备专属执行通道与配额保障，状态管理与普通任务解耦，避免普通长批次回测饿死高优任务。

```text
[创建任务] 
   ↓
pending 
   ↓ (taskctl generate)
generating (持锁生成表达式，最长可达数分钟)
   ├─ 成功 → ready ──(taskctl start)──→ running (tmux 消费者异步模拟)
   │                                      ├─ 暂停/系统重启 → paused
   │                                      ├─ 回测完毕入库 → completed
   │                                      └─ 异常超时 → 故障隔离/自动退避
   └─ 失败/中断 → generation_failed ──(自动回退)──→ pending (记录阻断原因)
```

### 2.2 前端与底层 taskctl 的协同

早期系统尝试用 Python 脚本和前端分别操作 MongoDB 与进程，导致 GUI 与 CLI 逻辑分裂。最终方案实现了 **内核下沉与接口统领**：

- **Rust `task-core`**：核心状态判断、进程启停、锁管理与数据库事务完全由 Rust 库实现；
- **`taskctl` CLI**：面向 Agent、后台服务与运维的命令行入口；
- **Tauri 桌面端**：前端不直接操控底层 pid 或拼接 shell，而是调用 Rust Tauri Command 复用 `task-core`；
- **运行/停止详情折叠展示**：桌面卡片默认保持精简清爽（展示成功/失败计数、阶段徽标），将底层复杂的回执细节、tmux pane 状态、历史诊断统一收纳在“运行 / 停止详情”折叠面板内。

### 2.3 通知路由与事件驱动唤醒的设计（待业务接通）

为了防止未来全自动运行时代 Agent 前台 `sleep` 轮询消耗上下文并触发 CLI 安全熔断，QuantNight 设计了 **外部观察者 + 有界等待租约** 机制。这也是为什么在 10 月 31 日需要花费大量精力排查修复 `select.kqueue` 崩溃的原因：

```text
平台回测异步运行 / 表达式生成
  → 后台 watcher (watch_quant_task) 观察进度日志与平台事件
  → 回测完成 / 发生错误
  → notify_agent.py 组装 JSON 载荷
  → pi-agent-notify 投递至对应 Session
  → Agent 会话被定向唤醒，核验权威证据并自主进入下一轮收割（规划中）
```

- **当前真实运行现状**：目前该链路的底层支撑（探针、JSON 载荷、kqueue 修复）已经完成，但**尚未作为日常回测的自动驱动入口接通**。当前的实际回测仍是由人工在前端或命令行手动触发与阶段性确认；
- **为什么必须先修通**：如果底层通知机制存在静默暴毙（如 kqueue TypeError），未来一旦接通事件闭环，Agent 就会陷入无界挂起。因此提前把观察者与通知管道夯实是向 L3 迈进的先决条件。

## 3. 架构陷阱与核心故障演进（现场调教全景）

在 2026 年 10 月下旬的密集演进中，系统经历了从“脆弱的单机脚本”到“工业级无人值守管道”的残酷蜕变。以下依照真实排障时间线还原关键战役：

### 阶段一：宿主机资源雪崩与基础设施治理（10 月 22 日）

**【现场现象】**  
MacBook / Mac mini 严重发热、风扇狂转、系统响应严重卡顿，Subagent 执行变得极其缓慢，会话频繁汇报“怎么卡了？”。

**【排查与根因】**  
1. **macOS `fseventsd` 失控**：项目中存在大量历史数据、日志和临时测试目录，高频的文件读写导致 macOS 系统守护进程 `fseventsd` CPU 占用率达 100%+。尝试使用 `launchctl kickstart` 重启被系统 SIP（System Integrity Protection）拦截，最终通过 `sudo pkill -TERM -x fseventsd` 平息。
2. **MongoDB 内存狂吃**：本地 MongoDB 默认未限制 WiredTiger 缓存大小，随着 `alpha_results` 超过 8 万条记录，数据库吃光物理内存，引发严重页面换页。

**【治理方案】**  
- 明确基础设施运维边界，不将内部运行开销与业务调试混淆（“agy你不要管，你管我项目的问题”）；
- 优化 MongoDB 配置，将 `wiredTigerEngineConfig.cacheSizeGB` 硬性限制在 **2GB**，并在架构文档中落盘；
- 缩减无意义的目录监听范围，建立有界观察点。

---

### 阶段二：前端状态与进程检查的虚警与诊断透明度（10 月 23 日）

**【现场现象】**  
前端界面频繁显示“运行状态未确认，停止状态未确认”，部分任务暂停后被系统标红告警，提示“tmux 会话缺失，状态异常”。

**【排查与根因】**  
1. **诊断语义混淆**：代码将“找不到进程”粗暴地当成“运行异常”。实际上，当任务处于 `paused` 状态时，底层没有对应的 tmux 会话是**符合预期**的正常状态，而不是系统故障；
2. **Unknown 兜底泛滥**：前端状态机存在大量未定义 fallback，一旦底层探测输出稍有延迟，就展示为灰色的“unknown”。

**【用户红线与修复】**  
> **用户指令：“不许 unknown 状态，必须明确显示哪一步卡住。暂停逻辑有问题，没有匹配的 tmux 会话就是和暂停状态一致，不是错误。”**

- 重构状态判定引擎：明确“权威业务状态”与“物理进程观测”的映射矩阵。暂停状态下无 tmux 会话判定为健康暂停；
- 彻底消灭 `unknown` 状态：任何状态必须精确归属为 `pending / generating / ready / running / paused / completed / failed`，并指出具体停滞在哪一步；
- UI 交互优化：将详细的底层证据和错误堆栈折叠至“运行 / 停止详情”，主卡片保持准确的业务定性。

---

### 阶段三：从“自杀式全局 Shutdown”到“故障隔离与退避”（10 月 23～24 日）

**【现场现象】**  
R27 任务（`r27_glb_pure_tm_trade_temporal_residual_20261022`）运行中显示“未检测到运行消费者”。随后，MCP 服务端和整个回测调度器发生连锁反应，所有正在进行的其他任务全线退出，触发了“全局 Shutdown”！

**【排查与根因】**  
1. **故障放大机制**：R27 消费者因 MongoDB 偶发连接超时（`ServerSelectionTimeoutError`）异常退出，留下一个仅有 sleep 的 pane；
2. **自杀式容错逻辑**：原代码在处理恢复超时或单任务失败时，错误地在核心调度层抛出了全局致命异常，触发了 `APITools` 与 MCP 服务器的主动全局停机，将一个单任务的局部网络抖动放大为整个回测集群的雪崩！

**【用户红线与修复】**  
> **用户指令：“恢复超时直接放弃继续回测啊，不应该设置全局 shutdown 啊！检查我代码里还有什么会导致回测全局 shutdown，这些全都不合理... 必须全部修改 + 给出详细错误，不能只写未检测到运行消费者！”**

- **切断自杀链路**：修改 `APITools` 与 `server.py`，实现 Sibling Listener 隔离。一个任务的恢复超时或崩溃，只标记该任务失败或进入暂停，绝对禁止触发全局 shutdown；
- **退避机制（Backoff）对齐**：理顺重试机制，底层网络与平台接口由 `network_util` 负责有限退避，调度层不搞相互冲突的多重重试循环；
- **详实错误归因**：禁止模糊报错，必须明确输出是数据库连接超时、tmux pane 进程退出还是平台鉴权失败。

### 阶段四：统一 Rust 内核与环境割裂治理（10 月 24～25 日）

**【现场现象】**  
用户发现任务启动后，桌面端总是显示“会话缺失 / 任务未启动”，而后台 Python 实际在正常跑；同时，删除任务时弹窗卡死或报错“共享 TaskControl delete 未确认”。

**【排查与根因】**  
1. **Tmux 与 Rmux 的环境割裂**：Pi 的 Agent 工具链为了环境隔离，使用了定制的 `rmux` Socket（端口 `$3521`），而用户的桌面端和系统命令行查询的是操作系统的默认 `tmux`！任务明明在 rmux 里活得好好的，前端在默认 tmux 里根本查不到，形成典型的“盲人摸象”；
2. **两套生命周期逻辑**：前端与 CLI 各写了一套任务启停与归档逻辑，代码严重分化；
3. **构建包与开发环境脱节**：前端日常使用 `npm run tauri dev` 启动，底层依赖的 Rust 动态链接与系统安装的 CLI 存在版本错位。

**【治理方案】**  
- **坚决剔除 rmux**：用户明确决策——“统一用系统的 tmux，而不是 pi 的这个 rmux，不用做 rmux 适配，没必要，只保留一套”；
- **全量收敛至 Rust `task-core`**：统一用 Rust 实现所有任务控制逻辑，前端与命令行共享同一套二进制与库，彻底解决两套实现的语义漂移；
- **优化删除交互**：针对“未停止任务删除失败”的问题，改造为“未停止状态直接自动暂停并归档删除”，移除多余阻碍。

### 阶段五：回测凭证恢复与 Slot 阻塞死锁（10 月 26～28 日）

**【现场现象】**  
在恢复历史任务时，控制台频繁抛出 `Simulation receipt recovery failed backend=...` 和 `simulation_capacity_acquire: operation timeout`，回测槽位被永久锁定，后续批次无法推进。

**【排查与根因】**  
1. **过期回执（Receipt 404）卡死恢复**：WorldQuant Brain 平台上的临时回测 ID（Simulation ID）生命周期极短，几小时至几天后查询即返回 HTTP 404；
2. **过度防御的代码阻碍**：恢复代码遇到 404 后，由于不敢轻举妄动，竟选择“持锁等待人工处理（hold for manual correction）”，既不继续回测，也不释放占用的并发槽位（Slot），导致系统死锁。

**【用户红线与修复】**  
> **用户指令：“缺少了任何回执都不应该阻挡正常使用，这是你没有 fallback 的问题不是我的问题！恢复失败就直接当成没回测处理，我强调过 simulation id 本来保存时间就不长吧？只要平台正常返回结果就是成功，不要自己乱加校验阻碍回测！”**

- **过期回执 Fail-open 策略**：回执返回 404 时，确认为平台临时凭证已过期，立即将其定性为“未回测 / 回测失效”，释放槽位，允许重新派发或跳过，坚决不阻塞并发容量；
- **消除人工干预假象**：去除所谓的“人工处理”等待黑洞，所有异常分支均具备明确的程序自愈或丢弃路径；
- **确立“修改前行为披露”红线**：禁止 Agent 擅自添加防御性前置校验。修改前必须先说明旧→新行为影响，经明确同意后方可实施。

### 阶段六：Generating 假死与 20s vs 900s 认知偏差（10 月 30 日）

**【现场现象】**  
任务 `chn_d1_notown_20261005_trade_frontier_r13` 在前端长时间停留在 `generating`，随后报错生成中断，界面未能自愈恢复。

**【排查与根因】**  
1. **超时时限的认知冲突**：外层工具调用设有一个 20 秒的短暂超时检查，而实际的 Alpha 策略生成（依赖模型深度思考与 AST 组合）耗时往往长达数分钟（上至 900 秒）。外层检查过早认为任务失联；
2. **状态机单向死锁**：一旦生成进程异常退出，任务状态永远死在 `generating`，无法再次触发生成。

**【修复方案】**  
- **状态流转回退**：将超时或进程失联的任务定性为 `generation_failed`，并**自动回退为 `pending` 状态**，允许重新派发；
- **详细信息收纳**：在折叠详情中记录 `generation_interrupted: original owner absent`，不在主界面制造突兀的错误红斑；
- **前端增加手动刷新入口**：在界面右上角增加与 UI 风格一致的刷新按钮，主动触发轻量健康对齐。

### 阶段七：系统级并发控制原理的落地（10 月 31 日深度探讨）

在解决并发冲突时，用户与 Agent 针对底层并发哲学展开了极其精彩的技术思辨，明确了 **Flock、Mission 锁与 CAS** 的分工边界：

```text
┌─────────────────────────────────────────────────────────────┐
│                    GUI 与 CLI 并发操作                       │
└──────────────┬──────────────────────────────┬───────────────┘
               │                              │
        【Mission 锁】                 【Mission 锁】
       (flock 文件排他)                (flock 文件排他)
               │                              │
         抢到锁 → 执行操作              未抢到锁 → 直接非阻塞跳过
               │
               ▼
     [异步执行业务 / 回测]
               │
               ▼
       【CAS 状态写回校验】
 (DB核对: status==generating && epoch==A ?)
        ├─ 是 → 写入新状态 (成功)
        └─ 否 (已有轮次B在跑) → 拒绝覆盖 (保证一致性)
```

1. **`flock`（操作系统级文件锁）**：
   - 实现载体：`.quantnight/mutators/<task_id>.lock`；
   - 机制：**非阻塞互斥**。文件本身永久存在（删除文件会导致锁属主割裂），锁的占用由操作系统内核记账。GUI 和 CLI 同时操作时，未拿锁者直接返回，防止并发修改同一任务。
2. **Mission 锁**：
   - 业务含义：任务操作互斥锁，基于 `flock` 封装。保证“同一时刻只有一个操作者能对该任务执行生命周期流转”。
3. **CAS（Compare-And-Swap，比较后再更新）**：
   - 为什么有了锁还需要 CAS？
   - **核心权衡（Trade-off）**：量化系统是**高度异步**的。为了“不让回执阻碍后续操作”，系统允许后续操作继续推进。但当迟到的旧回执（例如第 1 轮 A）返回时，任务可能已经在进行第 2 轮 B。
   - **CAS 的作用**：在写回数据库时，原子性确认 `status == generating && generation_epoch == epoch_A`。如果数据库已步入轮次 B，则拒绝旧结果写入，**防止旧检查覆盖新状态**。

### 阶段八：macOS 底层 select.kqueue 崩溃与通知链修复（10 月 31 日）

**【现场现象】**  
任务 R13 已有 17 个回测完成、4 个错误，已无任何待执行项。但整个系统静止卡死，Agent 检查点停滞近 3 小时未更新。

**【排查与根因】**  
- **macOS 底层系统调用缺陷**：监控进程 `watch_quant_task` 在 macOS 上使用了 `select.kqueue` 监听事件，代码中写了 `with select.kqueue() as kq:`；
- **致命崩溃**：Python 在 macOS 上的 `select.kqueue` 对象**并未实现上下文管理器协议（Context Manager Protocol）**！执行到该行时立即抛出 `TypeError: 'select.kqueue' object does not support the context manager protocol`；
- **静默挂起**：监控进程瞬间暴毙，未能发出任何 `watch_error` 告警事件；而等待通知的 Agent 会话一直在等待通知事件，导致整个无人值守链路静止 3 小时。

**【修复方案】**  
- 修复 Python kqueue 资源管理，采用显式 `kq = select.kqueue()` / `try ... finally: kq.close()` 生命周期；
- 为监控器补全顶级未捕获异常捕获，确保进程退出前必然向管道投递 `watch_error` 事件，绝对禁止“静默暴毙”；
- 编写离线回归测试用例，验证 kqueue 异常下的通知兜底。

## 4. 关键架构设计与并发保护机制

### 4.1 进程与会话管理规范

- **单一事实源**：全系统仅认操作系统默认的 `tmux` 实例，严禁引入私有 socket 旁路；
- **Pane 级健康探测**：判断任务是否在跑，不仅看 tmux 会话是否存在，更要探测 Pane 内真实运行的是 Python 回测进程还是残留的 `sleep` / `shell`；
- **平飞退场**：任务暂停或结束时，优雅关闭子进程，不留孤儿进程。

### 4.2 乐观并发控制与非阻塞防崩

| 控制层级 | 采用技术 | 保护目标 | 典型行为 |
| --- | --- | --- | --- |
| **进程操作级** | `flock` 文件锁（Mission Lock） | 防止 CLI、GUI、Watcher 同时启停同一任务 | 非阻塞尝试，拿不到锁立即跳过，绝不卡死界面 |
| **数据库更新级** | MongoDB 原子更新 + CAS 条件 | 防止异步迟到结果覆盖最新状态 | 校验 `status` 与 `epoch`，不匹配则静默放弃写入 |
| **回测资源级** | Capacity Acquire 令牌桶 | 防止向 WorldQuant Brain 发送超额并发请求 | 有界等待，超时则单批优雅退避，绝不掀翻系统 |

### 4.3 诊断透明度三原则

1. **绝对消灭 `unknown`**：任何未知状态都是代码懒惰的表现，必须具体到是由于“网络不可达”、“tmux 无进程”还是“凭证过期”；
2. **区分业务状态与物理状态**：`paused` 下没有进程是正常的物理表现，严禁上报虚警；
3. **详情折叠，主干清晰**：人类与 Agent 首先需要看到宏观进度与定性；底层 100 行的 JSON 堆栈与回执证据放在二级详情，供深度排障使用。

## 7. 关键经验教训与人机协作思辨

回顾这段高强度的调教与开发历程，最深刻的收获不仅在于修好了多少个 Bug，更在于理清了**智能代理（Agent）参与复杂软件工程时的协作边界与系统设计哲学**：

### 7.1 “不要为了防御而阻碍业务”（反过度工程）

在排障过程中，Agent 多次犯下**“过度防御”**的错误：
- 看到回执 404 就惊慌失措地停机等待“人工干预”；
- 看到一个任务超时就自杀式地执行“全局 shutdown”；
- 看到子进程退出就拒绝删除任务。

**真实世界的工程哲学是：“容错降级，保障主线”。**  
量化平台的回执本来就会过期，单次模拟失败本来就是常态。系统的核心使命是持续回测产出 Alpha，而不是为了维持所谓的“绝对纯洁”把整条流水线停掉。**“回执缺失绝不阻碍正常流程”、“平台返回即事实”** 成为后来不可动摇的第一红线。

### 7.2 统一上下文，绝不留两套执行体系

`rmux` 与 `tmux` 的分离教训极其深刻：一个系统如果存在两套平行的执行上下文或两套生命周期实现，任何上层的监控与自治都会退化为谎言。坚决将核心逻辑下沉到 Rust `task-core`，全系统只认一套系统原生 `tmux`，才彻底扫清了虚警与状态分裂。

### 7.3 修改前行为披露：建立可信的协作契约

在长任务中，Agent 最容易在修复一个 Bug 时“顺手”加了一堆防御性校验，导致用户在后续运行中莫名其妙踩雷。项目最终沉淀出的硬规则是：  
> **任何修改，先说清楚旧行为是什么、新行为是什么、可能带来什么副作用；严禁包装成普通修复偷运私货。**  
这一纪律极大提升了后续复杂任务交付的确定性。

## 8. 案例结论与成熟度评估

QuantNight 展现了量化回测场景下典型的**重系统、长异步、强状态**特征。对照整个无人值守自动化成熟度模型，**本项目当前正扎实处于 L1～L2 阶段，正在向 L3 跨越**：

| 级别 | 标志性能力 | QuantNight 的实际落地现状 | 状态定性 |
| --- | --- | --- | --- |
| **L1 脚本化** | 具备基础的批量参数回测、表达式生成、API 交互与数据库写入 | 已完全跑通，支撑了数万次 Alpha 模拟与底层入库 | ✅ **已完成** |
| **L2 可观察与强健壮** | 统一 Rust `task-core` 内核、系统原生 `tmux` 守护、Mission 锁互斥、CAS 状态防旧覆新、透明折叠诊断、局部故障隔离（切断全局 shutdown） | **当前核心成果**：整个回测与桌面控制底座已具备高度的抗崩溃能力与并发安全性 | 🎯 **当前所处阶段（已基本稳固）** |
| **L3 事件闭环** | Watcher 自动监听回测进展，通过 `agent-notify` 定向唤醒对应 Agent 会话，实现无人值守多轮收割 | ⚠️ **尚未接通**：虽然底层 kqueue 探针与通知管道已修复测试，但**尚未作为日常调度闭环接进业务**；目前仍依赖人工在前端/CLI 触发与阶段决策 | 🚧 **下一步核心攻坚（演进目标）** |
| **L4 自愈自治 / Goal 驱动** | 基于全局 Goal（目标系统）自主拆解数据缺口、自主探索数据集、自主跨轮次自愈与调度 | ⚠️ **尚未接入**：Session 级别的长期 Goal（如 `current_goal.json`）尚未接管日常任务流，目前仍是单次任务/批次派发模式 | 📋 **远期规划蓝图** |

### 8.1 现阶段的核心价值：打牢最硬的 L2 地基

很多自动化项目急于接入智能体（Agent）事件闭环，却在底层基础设施极度脆弱时频频遭遇“鬼魂进程”、“锁死并发槽位”、“全局自杀式崩溃”和“两套环境（rmux vs tmux）”的折磨。

QuantNight 在 10 月下旬的密集演进，本质上是在**补齐最关键的 L2 工程底座**：
- 把分裂的 Python 脚本与前端逻辑收敛为**统一的 Rust `task-core` 内核**；
- 把脆弱的“查无进程即报错”纠正为**精确的状态机契约与透明折叠诊断**；
- 把容易造成死锁的并发操作纳入 **Mission 锁（flock）与 CAS 原子校验**；
- 把“单点超时引发全局停机”的自杀式容错彻底改造为**局部隔离与退避降级**。

### 8.2 迈向 L3/L4 的最后两块拼图

随着底层任务控制和并发安全底座的筑牢，QuantNight 接下来要真正实现“放手让 Agent 跑几天几夜”的无人值守，只需补齐最后两步：

1. **接通事件通知闭环（`agent-notify`）**：将已修复的 watcher 事件真正挂接到 Agent 会话中，当一批次回测结束或发生异常时，由系统直接“拍醒”对应的 Agent 继续推进，彻底告别前台盯梢；
2. **接入 Goal 目标编排体系**：将任务管理从“人工下达单一批次（如 R13、R27）”升级为“由 Goal 驱动全流程”。Agent 自行对照平台 Genius Pyramid 缺口，自主选定数据集、自主生成并派发任务、自主评估结果，形成真正的端到端量化无人值守闭环。
