一、查看物理网卡（en0）与虚拟网卡（utun）的常用命令

在 macOS 终端中，可以通过以下命令快速识别当前生效的物理网卡、TUN 虚拟网卡以及系统默认路由。

1. 快速列出本机所有网卡接口

ifconfig -l
  • 输出示例：lo0 en0 en1 bridge0 utun0 utun1 utun7 ...
  • 含义：
    • en0（或 en1）：物理网卡（Wi-Fi 或有线网卡）。
    • utunX（如 utun7）：虚拟隧道网卡（VPN 或 Clash Verge 开启 TUN 模式后创建）。
    • lo0：本地环回接口（127.0.0.1）。

2. 查看网卡与硬件设备的对应关系（最直观）

networksetup -listallhardwareports
  • 作用：会明确标注出 Hardware Port: Wi-Fi -> Device: en0、Ethernet -> Device: en4 等，方便确认哪块是真实物理网卡。

3. 查看特定网卡详细信息

# 查看物理网卡状态与 IP
ifconfig en0

# 查看 TUN 虚拟网卡详情（若开启了 TUN 模式）
ifconfig utun7

4. 核心命令：如何正确验证流量是否被 TUN 接管？

[!WARNING] 注意：不要直接查 route get default！ Clash/VPN 的 TUN 模式为了防止断网和死循环，特意保留了系统的兜底默认路由（default -> en0）。 它是通过“最长前缀匹配原则”，注入了覆盖整个公网的细分路由（如 128.0/1、32/3 指向 utun7）。

因此，验证 TUN 是否接管，必须查询一个真实公网 IP（如 Google DNS 或 AWS IP）：

# 验证公共外网 IP
route get 8.8.8.8 | grep interface
# 输出：interface: utun7 （说明已被 TUN 成功接管！）

# 验证 DNS 是否被 TUN 接管。很多时候路由表走了 utun，但 DNS 泄露走运营商路由器，导致域名依然解析失败或被污染
scutil --dns | head -n 25
# 输出：首个解析器是 Fake-IP 198.18.0.2 说明接管成功

# 快速区分 Clash 混合端口（7897） 与 SSH 动态隧道（1080） 的归属
lsof -iTCP -sTCP:LISTEN -P -n | grep -E 'clash|verge|ssh'

# 验证 WorldQuant 所在的 AWS 弗吉尼亚 IP
route get 54.146.208.3 | grep interface
# 输出：interface: utun7 （说明 AWS 流量同样被 TUN 拦截并分流！）
  • 判定结论：
    • 若查询具体公网 IP 返回 interface: utun7，证明 TUN 模式正完美生效！
    • 若查询具体公网 IP 依然返回 interface: en0，说明 TUN 模式未开启或崩溃。

二、普通代理 vs TUN 模式的本质区别

工作模式 工作层级 运作机制 对“不自觉应用”（如 Python aiohttp / Docker）的处理
普通系统代理 L7 应用层 仅在本地监听端口（如 127.0.0.1:7897），属于“愿者上钩”。 完全无视。应用若未显式读取环境变量，直接绕过代理走原生网卡裸连。
TUN 模式 L3 网络层 操作系统底层插入虚拟网卡（utun），系统默认网关强行指向它。 强制接管。内核将所有发出的 IP 包捕获送入 TUN，无视应用是否配置了代理。 
flowchart TD
    subgraph Mode1["1. 普通系统代理 (未开 TUN - 应用层 L7)"]
        A1["应用程序 (如 Chrome/curl)"] -->|主动设置代理| B1["Clash 监听端口 127.0.0.1:7897"]
        A2["Python aiohttp (默认忽略代理)"] -->|强行走原生 Socket| C1["物理网卡 en0 (公网裸连, 易丢包卡死)"]
        B1 --> C1
    end

    subgraph Mode2["2. 开启 TUN 模式 (内核网络层 L3 强行接管)"]
        D1["应用程序 (无论 Python / Git / Docker)"] -->|发出的任何 IP 数据包| E1["虚拟网卡 utun (被内核全量拦截)"]
        E1 --> F1["Clash 内核接管 & 匹配分流规则"]
        F1 -->|规则匹配为 PROXY| G1["走海外低延迟专线 (加密加速)"]
        F1 -->|规则匹配为 DIRECT| H1["交回物理网卡 en0 真实直连"]
    end

[!IMPORTANT] macOS 系统的“系统代理 (System Proxy)”开关天然对 Terminal（zsh/bash）完全无效。终端发出的curl/python命令也属于“不自觉应用”。终端必须依赖环境变量或 TUN 强制接管。

三、全景对照表：什么情况下是直连？什么情况下走 Proxy？

很多网络误判（如“我明明没配代理，为什么也能访问？”或“明明能访问，为什么换台机器就超时？”）都源于混淆了应用自身行为与系统 TUN 接管。

下表涵盖了开发中的 8 种组合：

场景序号 TUN 模式
(L3 网络层)		 应用主动配代理
(传输协议/端口/代理隧道)		 Clash 规则设置
(目标域名)		 本机流转机制 最终物理出海路径 判定结论与典型生产案例
场景 1 已开启 (ON) ✔️ 主动配置 命中 PROXY 绕过 TUN，直连 127.0.0.1:7897 🔀 出口 A (海外专线) 【双保险 / 黄金组合】
应用跳过本地 DNS 查询，锁定 HTTP 隧道协议（免疫 socks5 bug），经专线高速出海。
场景 2 已开启 (ON) ✔️ 主动配置 命中 DIRECT 走 127.0.0.1:7897 入 Clash 后放行 🌐 出口 B (中枢直连) 【经审计直连】
虽然配置了代理环境变量，但目标为国内白名单，Clash 审计后放行至本地物理网卡。
👉 典型代表：配置全局代理时访问国内 aliyuncs.com / ts.net。
场景 3 已开启 (ON) ❌ 未配 / 忽略 命中 PROXY 被 utun7 虚拟网卡强行拦截抓取 🔀 出口 A (海外专线) 【透明接管 / 伪直连】
应用自以为直连，但内核将包塞入专线。毫秒级响应，却极易让人产生“直连真快”的错觉。
场景 4 已开启 (ON) ❌ 未配 / 忽略 命中 DIRECT 被 utun7 拦截后查验放行至 en0 🌐 出口 B (中枢直连) 【透明分流直连】
普通未配代理的应用访问国内网站，TUN 拦截后查规则放行回真实宽带。
👉 典型代表：浏览器访问普通国内网页。
场景 5 未开启 (OFF) ✔️ 主动配置 命中 PROXY 直连 127.0.0.1:7897 进入 Clash 🔀 出口 A (海外专线) 【传统应用层代理】
无全局虚拟网卡，但应用主动向 Clash 端口建立 HTTP CONNECT 隧道，绕过公网阻断，稳定秒开。
场景 6 未开启 (OFF) ✔️ 主动配置 命中 DIRECT 走 127.0.0.1:7897 入 Clash 后放行 🌐 出口 B (中枢直连) 【应用层直连放行】
即使未开 TUN，通过端口转发也能正确识别直连规则并走本地网卡。
👉 典型代表：业务脚本访问局域网 MongoDB。
场景 7 未开启 (OFF) ❌ 未配 / 忽略 命中 PROXY
(但完全无用)		 完全绕过 Clash，直冲物理网卡 ⚡ 出口 C (纯公网裸连) ⚠️ 【最危险的陷阱 / 规则失效】
Clash 规则哪怕写了 PROXY，但因为没开 TUN、应用也没配代理，数据包根本进不了 Clash 的门！
场景 8 未开启 (OFF) ❌ 未配 / 忽略 命中 DIRECT 完全绕过 Clash，直冲物理网卡 ⚡ 出口 C (纯公网裸连) 【纯物理原生网络】
无代理、无 TUN 介入，完全由本地 ISP 运营商公网路由决定成败。
