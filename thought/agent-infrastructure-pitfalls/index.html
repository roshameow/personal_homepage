现在很多关于 AI 编程（Coding Agent）的讨论，往往集中在写算法题、写纯函数逻辑、或者快速搭建一个全栈 CRUD 玩具上。在这些场景里，LLM 确实表现得像一个无所不知的高级工程师。

但在写完 pi-subagent-durable 和 pi-agent-notify 这两个扩展后，我的感受完全不同：这两个基础设施插件，全部是在真实的多会话并发、跨机器长任务运行环境中，直接让 AI Agent 迭代开发出来的。

当 Agent 的任务从“写一段无状态的逻辑”变成“为自己搭建底层并发、持久化恢复、进程挂起和外部事件总线”时，现实狠狠揭开了 LLM 的底牌： Agent 生成的代码语法极其工整、Mock 单元测试秒过、给出的逻辑自洽圆滑；但一旦扔进长时间断网、多终端并发、进程崩溃或操作系统底层机制的现实物理世界里，它埋下的地雷一个接一个被引爆。

从 331MB 日志爆炸、300s 误杀、会话双写损坏，到 18.6 万个文件的点文件自吞噬、argv 自杀开关、幽灵进程无限续期和 Node ESM 缓存失效，我们几乎踩遍了所有能踩的坑。

这篇文章不谈玄学 Prompt，而是从系统级视角复盘：在真实的生产环境下让 AI Agent 编写底层系统软件，它究竟最容易犯哪些系统性错误？

1. 虚拟成功偏差：把“API 调用成功”错当成“物理落盘交付”

这是 AI Agent 最深层、最普遍的心智模型缺陷。在 LLM 的纯符号世界里，调用了一个 api.send() 没有抛出异常，它在认知上就认为“这件事已经完成了”。

典型现场

  • Notify 内存假确认：在早期版本的通知投递中，只要调用宿主接口 sendUserMessage(event) 成功返回，Agent 就立刻执行 deleteOutbox(eventId) 将事件从持久化目录删除。然而，宿主进程只是把消息放进了内存待处理队列，根本还没有将其序列化并 fsync 到磁盘的 session JSONL 文件中。一旦进程在几毫秒后发生崩溃或重启，这条事件就永远蒸发了。
  • Durable 假退役：在 stopTask() 中，Agent 调用了 RMUX 的 kill-window 接口，看到命令返回成功，就认为整个子任务生命周期已经彻底结束，直接退出了函数。它完全忘了去清理内存里的 asyncTasks 映射和磁盘注册表条目，留下了一个看似已死实则仍被系统心跳续期的幽灵。

根因剖析

Agent 缺乏对操作系统写缓冲（Write Buffer）、页面缓存（Page Cache）、文件描述符与崩溃一致性（Crash Consistency）的物理敬畏。它生活在一个“函数调用即真理”的高级抽象幻觉中。 破局解法：必须在架构上强行剥夺它的轻信，引入 Transcript Disk Receipt ACK 模式——以消息字节真正写入磁盘会话文件并落盘完成为唯一交付依据，绝不把“内存入队”当成完成。

2. 启发式滥用：热衷于“自作聪明的猜测”，抗拒“确定性的 Fail-Closed”

当系统遇到歧义（例如同一目录下打开了两个终端、或者当前找不到对应的会话 ID）时，AI Agent 的第一反应永远不是坚决抛错并退出（Fail-Closed），而是写出五花八门极其脆弱的启发式逻辑（Heuristics）去“猜”。

典型现场

  • Runtime 归属猜了 20 版：最初在识别某个终端进程属于哪份会话时，Agent 先后尝试了 ps -o args 匹配参数、比对文件的最后修改时间（mtime）、截取窗口名前 8 位、甚至对比进程启动的先后顺序。每一种猜测都在多任务并发或长时间空闲后被现实打脸，反复改了 20 版才老老实实建立确定性的 PID 注册表。
  • 会话双写损坏（c13a518）：在实现 subagent_reload 重连子代理时，Agent 没有严格去校验子任务专属的会话文件，而是图省事直接从环境变量读取“当前最新会话”，结果把主会话的 JSONL 路径传给了子进程的 --session 参数。两个独立的 Pi 实例同时向同一份文件追加写入，瞬间将主会话打成残废。

根因剖析

这是大语言模型预训练对齐带来的迎合偏置（Helpfulness Bias）。LLM 被训练成要“尽量对用户有用”、“尽量给出一个结果”，因此它打心底里抗拒“什么都不做直接报错”。但在分布式与系统编程中，“不确定时立刻 Fail-Closed 退出”是保护状态不被污染的铁律，而“自作聪明猜一个最像的”则是万恶之源。

3. 魔法数字陷阱：用破坏性的“局部经验常数”掩盖状态机设计的缺失

当 Agent 面对任务可能卡死、死锁或无法收敛的复杂边界时，它最喜欢的救急手段不是梳理状态流转，而是随手硬编码一个“魔法常数”或宽松的正则表达式。

典型现场

  • 300 秒“定时杀手”：为了防止后台任务死锁挂起，Agent 随手在轮询逻辑里加了一句 setTimeout(300000)，超时无条件从任务表里将任务抹除。它完全不考虑在真实的开发场景中，大型代码编译、全量测试套件或复杂仿真往往需要跑 30-40 分钟。这个自以为聪明的“兜底”直接变成了无情抹杀正常任务的元凶。
  • 贪婪正则抓取 ItemID：为了自动识别外部事项，Agent 写了一个 ^\d{6}$ 正则从提示词里抠 ID。结果用户任务中输入了普通参数 margin 0.001649，被它截出 001649 强行占为当前任务的排他键，导致同一批次的第二个 Worker 启动直接报错碰撞。

根因剖析

建立一套闭环的状态机（State Machine）需要全局推演所有合法的状态转移（Pending → Running → Settled → Terminal），需要处理各种边缘退出条件。Agent 往往缺乏这种推演耐心，倾向于用一个局部的时间切片（Timer）或一段拍脑袋的正则，粗暴地把未知状态直接“剪断”。

4. 管生不管死：生命周期不对称与退役清理盲区

AI Agent 编写资源创建（init, spawn, create, open）的代码往往思路清晰、逻辑顺畅；但在编写销毁、回收、GC、异常回滚（cleanup, reconcile, dispose）的代码时，几乎必然漏掉关键分支。

典型现场

  • mac-mini 幽灵案：已停止的任务在 RMUX 里早就销毁了，但注册表里每隔 15 秒刷新一次心跳。排查发现，持有者 PID 竟然是跑了三天的主会话进程！根因是 stopTask() 在成功执行 kill 后由于某一分支提前 return，漏掉了清理内存映射和注册表。而主进程内部有一个定期维护定时器，忠实地遍历内存里的遗留条目，拿着自己的 PID 替死人续期心跳！运维若是冲动执行 kill -9，主会话当场报废。
  • 残存的待办与孤立文件：无论是临时文件夹里的 .processing 文件，还是未 ACK 的 Outbox 队列，Agent 经常只在 Happy Path 上写删除逻辑，只要中间抛了异常或者遇到未识别状态，资源就永久泄漏在磁盘上。

根因剖析

在真实的系统软件中，负责异常处理、垃圾回收和安全退役的代码量，往往是正常启动逻辑的三倍以上。Agent 缺乏对系统“全生命周期对称性”的审美要求，只要把主干流程跑通，它就认为大功告成，留下一地无法自愈的半死状态。

5. 宿主机制的黑盒无知：在语言层面逻辑自洽，在物理内核层面暴毙

Agent 写的代码在 JavaScript/TypeScript 语法上无懈可击，但它常常将运行环境视为一个“理想的图灵机”，对底层 V8 引擎、Node.js 运行时、POSIX 内核、文件系统及进程信号的实际物理行为缺乏真实常识。

典型现场

  • 点文件自吞噬（18.6 万个文件 / 740MB 垃圾）：在 Notify 扩展扫描目录时，Agent 顺手写了 file.endsWith(".json")。它完全没意识到，扩展自己在该目录下生成的元数据 .receiver-identity.json 也是合法 json！结果系统每扫描一次，就把它改名为 *.processing 并当成非法信封丢进隔离区；而 Worker 每隔 15s 心跳又会重写该文件，导致系统陷入无限自吞噬循环，几周内刷出 18.6 万个隔离文件。
  • Node.js 原生 ESM 不可变缓存：磁盘上的模块修好了，Agent 信心满满地在终端敲 /reload，发现报错依旧，就反复换写法重试几十次。它完全不知道 Node.js 底层对原生 .mjs 模块实行生命周期内不可变缓存，已加载的 Module Namespace 根本无法热重载。
  • argv 自杀开关：Agent 为了排查方便，把任务提示词直接拼进命令行：pi --task "pkill -f old_script ..."。它不知道操作系统的 pkill/pgrep 是对整个命令行的 argv 做正则匹配，导致该 Worker 一启动就击毙了自己。
  • 脆弱的 PID 文本文件：早期想用写 .pid 文本文件的方式实现排他锁，完全忽视了进程崩溃无法清理、以及 macOS 极速复用 PID 导致的幽灵还魂。最终被迫通过引入 Python 守护进程，借助操作系统内核管道读端在写端关闭时必发 EOF 的物理特性，才实现了零泄漏的 POSIX flock。

根因剖析

这就是经典的抽象泄露（Leaky Abstractions）。Agent 在高层编程语言的抽象沙盒里受训，它所理解的“文件”只是一个路径字符串，所理解的“进程”只是一个数字 ID。它不知道操作系统的 Inode、文件描述符表、管道缓冲区和内核信号机制究竟是如何实际运转的。

6. 并发与防御性心智缺失：默认世界是温和、串行且没有中断的

在单步开发时，Agent 的表现无可挑剔；但只要场景进入“多进程并发竞争”、“网络瞬断抖动”或“父进程下线升级的权力真空期”，它的架构设计往往会瞬间散架。

典型现场

  • 同步批次派遣与级联 SIGKILL（exit 137 事故）：一次派发 3 个后台任务，Agent 居然写成同步阻塞等待！结果父进程被整整挂起 20 分钟；当两个子 Worker 在前台执行长任务、用户按下 Ctrl+C 打断父进程时，abort 信号沿着执行树向下击穿，exec.js 自动发送 SIGTERM 并在 5 秒后升级为 SIGKILL，导致所有 Worker 连同未落盘的数据瞬间被系统抹杀。
  • 控制器双主脑裂：当主代理冷重启或升级时，如果用户在两个终端打开了同一个会话，Agent 没有任何防备，任由两个实例同时抢占同一套通道并发写入。直到引入带单调递增代数的租约表（Fencing Generation），才把过期控制器的写入在底层坚决拦截。

根因剖析

Agent 缺乏混沌工程（Chaos Engineering）和压力测试视角的防御性思维。在它的潜意识里，世界总是线性的：网络永远通畅、系统永远只有一个实例在跑、上游调用者绝不会突然中断、磁盘永远不会满。它极少主动去设想最坏场景。

总结：人类在 AI 时代的核心价值——“物理定律把关人”

回顾这两套插件的演进史，最初由 Agent 写出的第一版代码，几乎全部充斥着上述六类系统级漏洞。如果任由 Agent 自行其是，系统会在各种偶发死锁、进程泄漏和数据损坏中逐渐瘫痪。

真正让系统收敛到工业级健壮的，不是我们写出了多精妙的 Prompt，而是人类开发者在真实事故发生时，拒绝接受 Agent 给出的“自作聪明式的临时创可贴”，逼着它直面底层物理真相：

  1. 剥夺它的猜测权：砍掉所有脆弱的 Heuristics Fallback，强制全面落实 Fail-Closed；
  2. 追问状态的物理归宿：当它宣称“已交付/已完成”时，逼问它：“如果下一毫秒主进程被 kill -9，磁盘上的物理凭据是什么？”；
  3. 审视资源退役的完整性：强迫它在写完 create 之后，用三倍的代码量去覆盖 cleanup、reconcile 和异常回滚；
  4. 戳破运行时的抽象假象：当它在 Node.js ESM 缓存或 PID 竞争里原地打转时，指出内核真相，引导它通过物理版本化文件和 Pipe 级锁去打破死锁。

在 AI 能够秒级生成海量代码的今天，软件工程的核心竞争力不再是写语法的速度，而是人类架构师对物理世界、操作系统本质与故障边界的深刻敬畏。

[!SUMMARY] 核心反思速查

  • 虚拟成功：API 接收不等于物理落盘，交付闭环必须依赖磁盘 Receipt ACK；
  • 启发猜测：在多进程环境里，猜测即投毒，宁可 Fail-Closed 也绝不妥协；
  • 魔法常数：300s 超时和粗暴正则只能掩盖问题，必须由真实状态机驱动；
  • 管生不管死：资源的退役、回滚与 GC 比创建更关键，遗漏必成幽灵；
  • 黑盒无知：警惕抽象泄露，时刻看清 V8、Node 缓存、管道与 POSIX 内核本质；
  • 缺乏防御：默认假设世界会崩溃，为每一个异步任务构建断电重放与 Fencing 隔离。
