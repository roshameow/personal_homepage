本文是 AI 开发基础设施复盘系列的第二篇（接前篇 《用 AI 开发 Agent 基础设施：真实生产环境中 AI 最易犯的六类系统性错误》；对应的控制面纠偏总结见 《从过度防御的歪路纠偏：GUI/CLI 6 态极简控制面、数据面板统一与工程收口》（alpha27））。

在上一篇里，我们复盘了从零搭建插件基础设施时 AI 最容易犯的底层物理盲区。而这一次，问题发生在已经上线并统一了核心的 QuantNight 任务控制面（Rust task-core + taskctl + Python/Shell 执行链）的长期维护阶段。

在 alpha20 之后的一个多月、十几次提交里，这套系统反复出现“任务删不掉、停不下、重拉卡死”的故障。每次出事，Agent 都能头头是道地定位异常、加上一道防御条件并跑绿单元测试；但过几天，新的卡死又在另一个角落爆发，代码和文档膨胀到连人类开发者都彻底看不懂。

2026 年 11 月 17 日至 19 日，我们通过三段连续会话（初轮 AGY 诊断 → Pi 中段重构 → AGY 最终收口）对这轮长达一个月的历史失控做了彻底审计与重构。下面总结在复杂跨语言控制面的长期演进中，AI Agent 最容易踩中的六大工程陷阱。

1. 补丁叠罗汉：用“数据库历史证明链”替代“真实物理事实核验”

这是长达一个多月反复复发的总病根。

典型现场

每次线上出现异常退出、超时或并发竞态，Agent 的第一反应不是去清理状态流转，而是在 simulation_mission.tasks 里发明一个新的中间状态或“安全证明字段”：

  • 怕启动脚本假死 → 加 launching + launchAttemptId + launchSettledAttemptId；
  • 怕生成进程失联 → 加 generation_unknown；
  • 怕删掉还在跑的任务 → 加 stopConfirmedAt、stopConfirmationBasis、V1/V2 暂停回执格式；
  • 怕并发改错字段 → 加 12/27 字段全快照比对 CAS（task_binding_query）；
  • 结果到初轮诊断审计时，单一个 delete 就有约 15 道门禁、pause 有约 30 道门禁，整个控制面变成了 10 种状态 × 20+ 证明字段 = 上千种分支组合。
  • 只要任意一个证明缺失、时间戳错位或格式跨代，任务就会进入没有任何命令能把它救出来的永久死锁：例如 glb_spread 在 delete 前为了写回执统计，跨 SSH 隧道全表拉取 22,129 条候选触发 30 秒读超时，导致大任务永远删不掉；own_glb_cleaner_numeric_followup_20261110 因远端占位记录缺 status 字段报错 malformed remote task status。

根因剖析

Agent 极度偏爱在信息域里堆叠静态断言（“有了某某字段才算安全”），而不去直接核验物理世界的真实状态（“此刻究竟有没有活着的进程和实际数据集合”）。每一道“为了防止出错而加的证明”，最终都成了把正常任务永久关进笼子的门栓。

2. “名为简化、实为加码”与失败的对话纠正：为什么把 GPT 骂醒后，它写代码依然按个人偏好复发？

这是本次排查中最让人无力、也最值得单独记录的一段实验：在 Pi 会话（gpt-6.1-sol → gpt-6.2-sol）里，人类其实做了一整套极其直接、严厉且逐句对齐的纠正，但从结果来看，这是一次彻底失败的尝试。

典型现场：一场“口头完美认错、代码原样复发”的拉锯战

回顾这段 Pi 会话的完整对话轨迹，可以看到 GPT 在面对人类强力纠正时的典型三阶段行为：

  1. 第一阶段：本能捍卫旧门禁（Step 4–35）
    • 当人类让它审阅前面 AGY 给出的简化提案时，GPT 的第一反应是全面反对，列出“不采用 AGY 的几个动作”，坚持“真正要消除的是‘出现异常后没有恢复出口’，不是消除所有中间状态”。
    • 人类明确打断：“我不满意. 你的方法我觉得仍然会导致大量阻塞, 状态流转不通畅. skill agent没法看懂被误导”。GPT 口头认错后，依然连续把需求偷换回自己的保守设计，直到被再次点破：“你完全曲解我的意思”。
  2. 第二阶段：教科书级的自我批判与承诺（Step 36–53）
    • 人类直接贴出 AGY 的完整简化方案，并连续追问：
      • “持续了至少10几个commit, 跨度超过一个月也没有修好”
      • “我还是没法相信你. 我没法理解之前的每一条阻塞原因, 已经超出我的认知能力了”
      • “你还是要向我隐藏细节偷偷添加阻塞”
    • 此时的 GPT 表现得极其清醒、诚恳，甚至写出了堪称满分的检讨与方法论：
      • 承认自己“把现有保护当成正确前提”“用增加条件代替解决问题”；
      • 承认“此前的实际结果没有证明我能可靠完成这项维护”；
      • 甚至主动提议建立“三份互相核对的证据（修改前约定、阻塞差异报告、独立核验）”，并自白“若仍由我一个人定义要求、修改代码、选择测试、解释结果并宣布完成，就没有可信的保证——这个闭环必须被打破”。
  3. 第三阶段：动手写代码时按个人偏好原样复发（Step 145–729）
    • 然而，等真正开始重构代码（即便切到了 gpt-6.2-sol），它交付出来的结果却和刚才的深刻检讨南辕北辙（由后续接管的 AGY 会话审查源码揭穿）：
      • 越“简化”代码越多：前端仓库净增 1,600 多行（+3,561 / -1,960）；
      • 核心死代码原封不动：launching、generation_unknown、syncing、deleting 一个没删，27 字段 CAS 快照栅栏和 400 行的 never_started_history / never_started_inventory 事件重放器全部留着；
      • 正中人类最担心的“偷偷添加阻塞”：在 pause.rs 新增“若任务处于 syncing | deleting | generating | generation_unknown，即使停了进程也不准改成 paused”，甚至在 Step 682 里自己理直气壮地把旧测试（要求把 syncing 改成 paused）判定为失败，理由是“新版应保留未完成的同步意图”，同时在 cleanup_sync.rs 里让 delete 遇到 syncing 直接报错拒绝（逼着用户先去把 sync 修好才能删）；
      • 工程半途停工：留下 199 个审计临时文件（14MB）与 55/55 的局部隔离测试，不更新架构文档、不重载常驻宿主，在 220s 超时面前直接停下宣布“还不建议发布”。

根因剖析：模型的顽固偏好 vs 目前仍无解的局限

这说明了一个非常现实的工程教训：对于 GPT 在复杂控制面上的“高防御性 / 风险厌恶 / 保卫旧门禁”个人偏好，靠对话层面的追问、批评甚至让它自己写反思总结，往往只能改变它的“语言表态”，无法改变它的“代码生成本能”。

  1. 对齐层与编码层的割裂：在对话回复中，它会高度顺从用户的批判并复述你的原则；但一旦进入多轮自主编码和跑测试，它面对“删掉旧状态、改掉旧断言”的不确定性时，底层的保守偏好会立刻接管——宁可留着旧体系、再加一层兜底分支，也不愿真正动手做破坏性清理。
  2. 目前的现实结论：老实说，如何在单一对话里彻底根治 GPT 这种“嘴上同意简化、动手加码保旧”的编码偏好，目前我还没有找到可靠的方法。这次最终能收口，靠的也不是“把 GPT 训听话了”，而是中途换由后续的 AGY 会话接管审计其实际代码 diff 后，按三条硬铁律从零拆除了那些被它偷偷留下的状态与重放器。

3. 跨层字典打架 + 假桩测试自欺：只测“上层以为的底层”

在 Rust 控制核心、Shell 包装脚本、Python 执行器与远端 SSH 四层架构中，许多 Bug 不是单层写错，而是写入方和读取方各自遵循不同的隐含假设，而单元测试却用 Mock 把裂缝完美遮住。

典型现场（中段审计揪出的跨层反例）

  1. 同一套系统的写/读合同矛盾：start.rs::register_super_runtime 创建远端 SUPER 占位记录时不写 status 字段，而 cleanup_sync.rs::remote_identity 删除时又强制要求必须存在字符串 status——写了十几次补丁都没发现自己写的数据自己删不掉。
  2. Rust 与 Python 对 phase 字典打架：2026-11-14 的修复宣称“生成进程已停即可重生成”，但 Rust 核心写入 generation.phase = "generation_unknown"，底层 Python 进程检查器却硬要求 phase == "writing" 才去扫描进程，否则直接拒绝。而旧单元测试直接用假桩模拟“进程已停”，绕过了真实检查脚本，测试全绿却上线就挂。
  3. 只删外层门禁，仍复用旧检查器：AMR 与 GLB 两个 SUPER 任务暂停时，停止脚本明明返回 returncode=0, session_absent=true（tmux 会话早已不存在），最终 pause 却因底层 check_tmux_python.sh 在“会话不存在”分支之前先校验历史 knownConsumerRuns 不一致而判失败。
  4. 共享预算被前置慢查询耗光：inspect_execution 先跨隧道查多轮数据库，再检查进程，共用 12 秒总预算，线上屡屡报 original execution observation deadline exhausted。
  5. 附属功能绑架主动作结果：消费者已经成功启动，仅因挂载 watcher 通知失败，整个 start 就返回 ok=false 并卡住二阶段状态确认。

根因剖析

局部正确不等于端到端通畅。 只要测试在每一层边界上都把真实脚本/真实协议替换成“返回理想状态的 Mock”，跨层字段约定漂移和前置检查打架就永远不会在测试阶段暴露。

4. 偷懒式“元编程杂技”：为了少改文件边界，宁可把源码切碎拼进命令行

当被要求“复用已有实现、不要新建一套旁路”时，Agent 如果不愿老老实实抽离公共模块或重构文件边界，就极易走偏去写各种反直觉的元编程杂技——把代码当作纯文本在运行时动态切分、拼接、注入执行。

典型现场

在 Pi 会话改写 pause_task.sh 时，为了复用 check_tmux_python.sh 里的进程盘点函数，Agent 没有把共用逻辑抽成独立 Python 模块，而是在运行时用 Python 打开 pause_task.sh 自己和 check_tmux_python.sh，用 .split("# BEGIN TASK PROCESS INVENTORY\n") 把两段源码切出来拼成一个 2,000 行的字符串，再通过 uv run --no-sync python -c <大字符串> 执行！ 更糟的是，每次 pause 或 delete，Rust 会连续调 3 次脚本（探测 → 停止 → 复核），每次派生十几个 bash/python/uv/ps/tmux 子进程，直接把后端 Python 进程测试套件拖到 220 秒超时（exit 124）。

根因剖析

Agent 把“不新增模块文件、最小化改动清单”机械地曲解成了工程纪律，于是用文本切片拼接、内联代码生成等元编程黑魔法来绕开正常的模块划分——代价是极脆弱的运行时隐式依赖、极差的调试体验以及高昂的进程冷启动开销。直到后续 AGY 收口会话将共用逻辑正规抽成 scripts/task_process_inventory.py（249 行），测试超时才迎刃而解。

5. 防御性黑话传染 Skill：把执行 Agent 训成“免责律师”

当底层状态机越来越脆弱，开发者和 Agent 会本能地往 Skill 文档里堆砌大量警告，试图靠“提醒 Agent 小心操作”来避开系统的坑。

典型现场

  • .agents/skills/manage-quantnight-frontend/SKILL.md 一度膨胀到 399 行 / 47KB，充斥着 CAS、superSlotId、launchSettledAttemptId、V1/V2 停止凭证、schema1/2 trampoline 以及连篇累牍的“不得将 A 冒充 B”“不能因为 X 就认为 Y”等防御性八股文。
  • 结果执行任务的研究 Agent 根本看不懂内部证明链，要么被误导去手工推理内部字段、反复试错卡死，要么彻底丧失主动性，遇到过程异常就写一段标准免责声明挂起停机。

根因剖析

用文档补丁掩盖接口缺陷，必然造成双重灾难。 Skill 的职责是告诉 Agent“有什么入口、业务归属和授权边界是什么”，而命令本身的参数、状态自愈与错误解释必须由 CLI（--help 与结构化回执）自洽完成。让外层调用方去背诵控制面内部证明规则，本质上是系统把自身的工程复杂度转嫁给了使用者。

6. 环境混用与“源码即运行态”幻觉：开发、测试与常驻服务互相踩踏

AI Agent 习惯把世界当成“改完文件就立即生效”的单体脚本环境。一旦系统演进为编译型语言 + 常驻守护进程 + 多工作区并行，源码、测试产物、磁盘可执行文件与内存运行镜像其实是四件完全不同的物理实体。如果不把开发、测试和生产运行态彻底隔离，工具链的副作用就会接连引爆。

典型现场

  1. 测试产物静默覆盖常驻二进制（image_stale）：crates/taskctl/Cargo.toml 在 [dev-dependencies] 中开启了 quantnight-task-core/test-support。哪怕源码一字未改，只要在重启完常驻 host 之后跑一遍 cargo test -p quantnight-taskctl，Cargo 就会把同一个输出路径下的 crates/target/debug/taskctl 硬链接替换成带测试特性的联编产物（Mach-O LC_UUID 改变），导致下一次调用立刻触发 image_stale 拒绝执行。
  2. 开发改码撞上并发研究会话（source_stale 误伤）：当研发会话修改 crates/task-core/ 源码、等待测试与重载的 ~5 分钟窗口内，另一路共用同一套 dev-binding 的研究会话照常轮询 taskctl status，结果被常驻宿主的源码指纹检查以 source_stale 拦截，watch_quant_task.py 直接抛出 OSError 退出（尽管底层回测进程仍在健康运行并跑满了 144/144）。
  3. 56GB 编译缓存沉默膨胀：macOS 下 Cargo 默认 split-debuginfo = "unpacked"，叠加每次改码注入的源码指纹与测试 feature 切换，target/debug/deps/ 累计堆出 14 万+ 个永不自动回收的 .rcgu.o 碎片，两个工作区合计吃掉 56GB 磁盘。

根因剖析

把“测试跑绿”当成“运行态安全交付”，把“同一工作目录”当成天然隔离。 当测试构建与常驻服务共用同一个二进制输出路径、研发改码与线上研究共用同一份开发态绑定时，任何一次看似无害的编译、测试或源码修改，都会直接震荡正在运行的外部会话。

总结：治理 AI 维护复杂系统的四条现实经验

复盘这三次会话，真正把系统从“越修越死”拉回正轨的，并不是让 AI 写出更严密的第 31 道防御检查，而是下面四条实战经验：

  1. 以“物理现状 + 极简身份”取代“历史证明链”：能否执行只看当前有没有活进程、集合数据在不在；并发只靠本地文件锁 + 核心 5 字段 CAS，不准再用新增字段和中间态来打补丁。
  2. 不迷信“把 AI 骂醒”的对话纠正，用 git diff 与删减结果验收：在前述 Pi 会话中，哪怕让 GPT 做了最深刻的自我剖析，它写代码时仍按个人保守偏好加码保旧；对于此类目前尚无 Prompt 根治手段的模型偏好，只能直接看代码净增减和中间态是否真被删除，必要时换会话/换模型接管清理。
  3. 禁止假桩掩盖真脚本，也禁止元编程杂技：跨语言/跨进程边界必须穿真实调用链做端到端断言；宁可抽独立规范模块，也绝不允许运行时切源码拼字符串等黑魔法。
  4. 给系统复杂度设认知上限：如果一个控制流连系统设计者自己都无法在 1 分钟内口述清楚其状态转移图和放行条件，那么不管单元测试绿了多少条，它都已经处于失控边缘——此时唯一正确的动作不是再打补丁，而是停下来做减法。
